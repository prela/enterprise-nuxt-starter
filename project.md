# project.md

Owner-locked Bible. Agents follow it. They do not edit this file unless the owner has approved a specific proposed diff.

## Change protocol

1. An agent (or the project manager) proposes a patch: the diff, why it is needed, and what it would break.
2. The owner discusses and either rejects, amends, or approves.
3. Only after explicit owner approval may this file be modified.

Glossary lives in `CONTEXT.md`. Hard-to-reverse decisions live in `docs/adr/`. Those may be updated when a term or decision crystallizes; this file may not.

## Goal

The Starter is a production-ready Nuxt 4 foundation: published Nuxt Layers plus a Playground application that proves them. Products (PMS, rental, marketing site, …) are separate deployable applications that `extends` those Layers. This repository is not itself a Product.

Work is Domain-Driven (ubiquitous language, Tiers, ports) and Test-Driven (red–green–refactor). Each Nuxt Layer exposes a small public interface; Tiers inside a Layer stay replaceable behind that interface.

## Vocabulary

Use `CONTEXT.md` as the glossary. In particular: **Product** not “service”; **Nuxt Layer** vs **Tier**; **Identity** not “auth module”; **Application service** for domain logic; **Host** / **Playground**; **Work package** (not a SemVer tag); **Bible** for this file.

## Tech Stack

- **Language:** TypeScript only (strict). Vue SFC: `<script setup lang="ts">`.
- **Framework:** Nuxt 4, Vite, unjs / Nitro.
- **v1 Nuxt Layers:** `core`, `ui`, `identity`.
- **v1 modules:** Nuxt UI, VueUse, Pinia, Zod, Better Auth (Identity adapter), nuxt-security (baseline headers).
- **Data:** PostgreSQL via Drizzle ORM. Not MySQL.
- **Tooling:** pnpm, Antfu ESLint, Vitest, Playwright, Docker, GitHub Actions, Coolify on Hetzner VPS.

Post-v1 catalogue (not v1): Nuxt SEO, Nuxt Content, i18n, `@nuxt/image` / `@nuxt/fonts` / `@nuxt/scripts` as a full suite.

## Patterns

### Critical requirements

The solution MUST:

- Model the domain (DDD) and drive implementation with TDD.
- Distribute capability as Nuxt Layers; structure code inside them as Tiers (presentation, application, domain, infrastructure).
- Keep Products able to take or omit a Nuxt Layer without editing Starter internals.
- Document each Nuxt Layer’s public interface.

### Core foundation

- Strict TypeScript; auto-imports configured per Layer.
- Antfu ESLint; lint and typecheck at zero errors.
- UI: Nuxt UI + Tailwind, mobile-first, dark/light. If Nuxt UI has no control, shadcn-vue. Atomic design only as far as screens in scope require — not an encyclopedia in v1.
- Accessibility: WCAG 2.2 AA on shipped UI.
- Zod at every runtime boundary (env, payloads, query params).
- Strong typing at Layer public interfaces and HTTP contracts.

### Core design principles

- Separation of concerns: Nuxt Layers for distribution; Tiers for code.
- Dependency inversion: application/domain Tiers depend on ports, not Drizzle/Better Auth.
- Loose coupling: Layers communicate through public interfaces, not deep imports.
- High cohesion: Identity persistence lives in the Identity Layer, not in `core`.
- Testability: each Tier is testable with fakes at its ports.

### v1 pipeline (required)

- Hybrid rendering via route rules as soon as there is more than one kind of page; Playground Identity pages are SSR.
- `nuxt-security` with CSP in report-only first, then enforce; CSRF and baseline headers.
- Health and readiness endpoints (no-cache).
- Pinia stores stay thin; logic lives in application services.
- Testing: Vitest (unit/integration), Playwright (E2E of the Identity slice).
- Docker Compose (Playground + PostgreSQL); GitHub Actions CI; Coolify preview from `develop`; production from a SemVer tag on `main`.

## Constraints

- Lint zero errors; typecheck zero errors.
- Coverage: 80% global CI gate; 95% on domain and application-service modules. Do not chase 95% on Vue glue, generated types, or Layer wiring.
- No global installs; only repo-defined scripts and tools.
- No breaking change to a Nuxt Layer’s public interface unless a MAJOR version bump is planned (in 0.x, MAJOR is the `0.Y` bump — see Versioning).
- No file moves across Nuxt Layer boundaries without explicit instruction.
- Prioritize correctness, maintainability, and security over extra catalogue features.
- Do not assume; ask. Do not edit this Bible without owner approval.

## Git

Simplified GitFlow (see `docs/adr/0004-simplified-gitflow.md`):

- **`develop`** — default branch, integration. Preview deploy of the Playground.
- **`feature/<work-package-id>-<slug>`** — from `develop`, PR back to `develop`. One work package per branch. Agents never commit directly to `develop` or `main`.
- **`main`** — protected. Receives a release PR from `develop`. Production deploy from a SemVer tag on `main`.
- **`hotfix/<slug>`** — from `main`; merge to `main` and back to `develop`.
- No `release/*` branches until 1.0 has a release cadence.

## Versioning

Lockstep SemVer for the whole Starter (all Nuxt Layers share one version). See `docs/adr/0005-lockstep-semver.md`.

- `0.y.z` until the first production Product depends on the Starter (breaking public interfaces allowed with a minor bump in 0.x).
- Then `1.0.0`. After that: MAJOR = breaking public Layer interface; MINOR = backward-compatible capability or new Layer; PATCH = fixes.
- Conventional Commits (`feat:`, `fix:`, `BREAKING CHANGE:`) so the changelog is mechanical.
- Work package IDs (`0.1`, `1.1`, `3.3`, …) label tickets and branches. They are not SemVer tags and are not mapped onto `0.y.z`.

## Public Layer interface

See `docs/adr/0008-enforce-public-layer-interface.md`. The Host and future Products import only a Layer’s documented public entrypoints. Deep imports of another Layer’s Tiers are a CI failure. Internal Tiers may import within the same Layer.

## Multi-agent protocol

- One work package = one `feature/<work-package-id>-<slug>` branch = one PR into `develop`.
- An agent claims a work package only if every dependency is merged.
- TDD (red first) on Identity work packages and Playground E2E.
- No Bible edits without owner approval.
- No crossing Nuxt Layer boundaries in one PR except the Host work package that `extends` them.
- If blocked, stop and write on the ticket; do not start the next work package.

Phase 0 includes a public GitHub repository named `enterprise-nuxt-starter` (public so GitHub Free can enforce branch protection on `develop` and `main`; private + protection needs Pro). The owner creates or connects the remote; agents do not push until that remote and branch protection exist.

## Identity

Identity is an optional Starter Nuxt Layer behind a port (see `docs/adr/0002-identity-as-starter-port.md`). First adapter: Better Auth, self-hosted, Drizzle + PostgreSQL, email/password and httpOnly session cookie (`docs/adr/0006-better-auth-first-adapter.md`). Hosted IdPs (Clerk, Auth0, Supabase Auth) are not the core. OAuth providers are later adapters. A Product may omit the Identity Layer.

## Starter v1

Thin vertical slice, not the catalogue:

- Playground: register, log in, one protected page, log out.
- Nuxt Layers: `core`, `ui` (only what those screens need), `identity`.
- Drizzle migrations, Docker Compose, GitHub Actions (lint, typecheck, unit, e2e on PRs to `develop`).
- Preview deploy of Playground from `develop`; production deploy of Playground to Coolify on a `main` tag.

### v1 non-goals

## Future-proof best practices

Catalogue and defaults for after v1. Do not implement these in v1 unless a work package explicitly says so.

### Architecture and boundaries

- Nuxt Layers: `core` (base config, composition utilities), `ui` (design system), `identity`, later `content` (Content v3) and other Layers as Products demand them. Application logic lives in application services behind ports; data access in infrastructure repositories.
- Keep Layers independently testable. Export only the public interface (types, composables, documented entrypoints) at Layer boundaries.

### Rendering, caching, and delivery

- Hybrid rendering with route rules (`prerender`, `swr`, `isr`, `ssr: false`) per route. Cache static-like pages; keep admin SSR or CSR as needed.

```ts
// Example only — not v1 Playground routes
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },
    '/docs/**': { swr: 3600 },
    '/blog/**': { isr: 3600 },
    '/admin/**': { ssr: false },
    '/api/**': { cors: true },
  },
})
```

- Later: `@nuxt/image` with IPX in dev and CDN in prod; `@nuxt/fonts` and `@nuxt/scripts`.

### Content v3 (post-v1)

- Collections in `content.config.ts` with Zod schemas. `queryCollection`, `queryCollectionNavigation`, `queryCollectionItemSurroundings`.

### State, types, and validation

- Pinia, strict, SSR-safe, thin stores.
- Zod for env, payloads, query params. Reusable types and type guards.

### Security and headers

- `nuxt-security` with nonce CSP (`'nonce-{{nonce}}'`), report-only then enforce. `/api/csp-report` with rate limiting.
- Consistent security headers; route-specific exceptions in `routeRules.headers`.

### Performance

- Nuxt performance guide: `Lazy*`, lazy hydration, smart prefetch, `useAsyncData`/`useFetch`, bundle analysis.
- Prefer built-in modules over ad-hoc solutions. Cache at Nitro and CDN.

### Testing and CI/CD (TDD)

- Red–green–refactor. Unit tests for composables and application services, integration tests around server routes, E2E for critical flows.
- CI: lint, typecheck, unit, e2e. Preview deploys with smoke checks for headers, CSP, and caching.

### Observability and resilience

- Structured server logging, UI error boundaries, Nitro error handlers. Health and readiness, no-cache on those routes.
